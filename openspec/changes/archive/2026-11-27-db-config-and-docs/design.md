## Context

See proposal.md for the symptoms. Where each comes from today:

- `detectConnection` (`variant-config/autodetect.ts`) returns `filename: <dir>/.cache/variants/variants.db` when nothing is detected. From the environment it reads `SQLITE_PATH` into `filename` and `SQLITE_DATABASE` into `database`, and does not look at a `sqlite:` URL. The loaded configuration skips detection for an explicit `db.type: sqlite` (`loadConfig`), so such a configuration has no file.
- `SqliteAdapter` (`variant-api/db/sqlite.ts`) computes the file as `dirname(filename)/<slug>.db`, or `<stateDir>/<slug>.db` without a `filename`; it only honors `${slug}`. It resolves nothing, so a relative `filename` follows the process cwd. `list()` reads only `stateDir`.
- `createVariant` and `prepareRun` compute the target as `slug === "main" ? (db.schema ?? "public") : adapter.target(slug)`: the PostgreSQL rule, applied to SQLite. `create` writes `type: sqlite`, `target: public` into `state.yaml`, and `variant config` reads it back as `runtime.db.filename: public`.
- `recordPairs` (`variant-cli/text.ts`) prints `target` and `type`; `VariantRecord` has no field that says where the data is.
- `legacy.ts` already renames old keys (`instances`, `reservedPorts`) in memory and in text, with notices; `variant-cli` rewrites the file afterwards.

## Goals / Non-Goals

**Goals:**
- One function turns (`db.database`, slug, variant directory) into the absolute SQLite file, and every caller uses it: adapter, `create`, `prepareRun`, `list`, `implode`, runtime state.
- One setting for the database name or file: `db.database`.
- `variant create` shows where the data is, without a secret.
- A Database page a reader can copy from.

**Non-Goals:**
- Writing the default into `variants.yaml` (the existing "Nothing detected" scenario stays).
- A table-prefix or schema mode for SQLite, or `db.multi` on SQLite (still refused).
- Changing the PostgreSQL or MySQL target of `main`, or the `status`/`list` text layouts.
- A new redaction format for `status`: it keeps `***` for `db.password`.

## Decisions

1. **`db.database` replaces `db.filename`; detection keeps its inputs.** The two settings named one thing for different types. `database` already carries `SQLITE_DATABASE`; `SQLITE_PATH` and the `sqlite:` URL file now feed it too. `filename` leaves `DbConfigSchema`, so the generated JSON schema and the editor completion drop it. `legacy.ts` gets one more rename (`db.filename` to `db.database`, in memory, in text, and in `runtime.yaml`), with the same notice and file-rewrite path as `instances`. Both present: `database` wins. Alternative: keep `filename` as a silent alias. Rejected: two names stay documented forever, and the user asked to sunset it.
2. **The default is the template `.cache/variants/${slug}.sqlite`, relative.** The printed value is the real value; `main` gets its own file (`main.sqlite`), so a slug called `variants` cannot collide. The extension changes from `.db` to `.sqlite` as asked. Existing `.db` files of earlier versions are kept by a migration (decision 11), not renamed. Alternative: `variants.sqlite` for `main` with `<slug>.sqlite` beside it. Rejected: the printed value would still not describe a variant.
3. **A relative path resolves in the variant's own directory.** The base is the worktree `<variant.root>/<variant.prefix><slug>` (known without the worktree existing), the main checkout for `main`, and the directory of `variants.yaml` when the library runs without worktrees (`worktree: false`). That gives every variant a private file by construction, even when `db.database` has no `${slug}` (`abc.sqlite` becomes `_v-demo/abc.sqlite`), and implode, which removes the worktree, takes the file with it. The `config` output prints the unresolved text; it cannot print one absolute path for all slugs. Alternative: resolve against `variants.yaml`. Rejected by the request: a shared directory makes the slug the only separator.
4. **Absolute paths keep a separator rule.** An absolute file without `${slug}` would be shared by all slugs. It is the file of `main`; others get `<slug><ext>` beside it (the earlier sibling rule, with the extension of the given file). A slug that maps onto the file of `main` throws, naming the slug and `db.database`. A relative path cannot collide, so no check. Alternative: refuse an absolute path without `${slug}`. Rejected: `SQLITE_DATABASE=/path/app.sqlite` from the environment is a normal shape and must keep working.
5. **One helper, in `variant-api/db/sqlite.ts`.** `sqliteTarget({ database, slug, directory })` holds the `main`, template, sibling and collision rules. `SqliteAdapter` receives a `directoryOf(slug)` function from the client (worktree path from `variant.root`, `variant.prefix`, `variant.main`), instead of `stateDir`. `createVariant` and `prepareRun` replace the `schema ?? "public"` expression with `targetFor(context, slug)`: `adapter.target(slug)` for SQLite, the old rule for the other database types. The `stateDir` fallback of the adapter stays for callers without configuration (tests).
6. **`list` looks where the files can be.** Absolute: scan the directory and match the base name against the template (`${slug}` captures the slug; without a template `<slug><ext>`), dropping `main`. Relative: the catalog is the slugs known from worktree directories and state files whose resolved file exists. A relative path has no shared directory to scan. `main` is not in the catalog; its record comes from its state file.
7. **`state.yaml` of `main` heals.** `rememberCreated` returns early when `createdAt` exists, so the `target: public` of an earlier version would stay. For SQLite it also rewrites `db` when the recorded target differs from the resolved file; `createdAt` stays. No migration notice: `state.yaml` is derived runtime state. `runtime.db` for SQLite is `{ type, database }`; the `runtime.yaml` dump of an earlier version with `filename` is read as `database`.
8. **`database` on the record is computed in `variant-api`.** `VariantRecord` gets `database: string` (Zod schema first). `describeDatabase(config.db, slug)` returns, for SQLite, `db.database` with `${slug}` replaced and nothing else changed (relative stays relative to the worktree, absolute stays absolute; `target` keeps the absolute path), and for the server types a URL: from `db.url` when set, else `scheme://user[:***]@host[:port]/database`. Only the password part is replaced. `postgres://` for `postgres`, `mysql://` for `mysql` (MariaDB included). It does not need the worktree to exist, so a database-only record has it too. Alternative: have the CLI build the string from the config. Rejected: the CLI has no config, and the MCP server and extension get the same record.
9. **One text layout for `create`, `status` and `list`.** `recordPairs` in `variant-cli/text.ts` becomes `worktree`, `database`, then `schema` for the server types (from `target`), then `mode`, `uptime`, `url`, `log`. `create` and `status` (and so `list --verbose`) share it, so they cannot drift again. `formatTable` adds `database` as the last column, so a long URL never pushes the others. `up` and `watch` keep their `target` line: they are not part of the request. `status` keeps its `runtime` block, where `db.database` is the absolute file.
10. **`init` writes `database`.** Detection puts the file into `database`, so the existing field loop writes it; a defaulted file (`source: "default"`) is not written.
11. **The former location is migrated by the config layer, in memory and in text.** `findFormerSqliteDatabase(configDir)` (new, in `variant-config`; it touches the file system, so it stays apart from the pure text functions) returns `<abs dir>/.cache/variants/${slug}.db` when `<dir>/.cache/variants/` holds a `*.db` file. `loadConfig` calls it only when the type is SQLite and `database` came from neither `variants.yaml` nor the environment, sets `db.database` to the value and adds a notice. `migrateText(text, { database })` sets `db.database` (creating `db` and `type: sqlite` when missing, keeping comments and order); the `variant-cli` migration step, which already has the config, passes the value and writes under the existing rules (clean tracked file, or a `~` backup, never with uncommitted changes, not under `CI`). The path is absolute because the old files were shared by all worktrees of the main checkout, and a relative path would now mean one directory per worktree. Alternative: a runtime fallback that silently uses the old directory. Rejected: the request is that `db.database` is populated, and a silent fallback leaves the file unaware. An old explicit `db.filename` is only renamed: its meaning (sibling files of an arbitrary directory, relative to the cwd of the time) cannot be rebuilt reliably.
12. **Docs.** `docs/guide/database.md` is new, between CLI and Runtime in the sidebar; Configuration moves ahead of CLI. The page has three sections, each with explicit YAML, a `text` file tree with `mise.local.toml` and a TOML `[env]` block. All passwords are placeholders. `docs/guide/configuration.md` loses `db.filename`, gains the SQLite note on `db.database` and links to the page. Alternative: put the examples into Configuration. Rejected: that page is a key reference with one heading per key.

## Risks / Trade-offs

- [`db.filename` stops being valid] → the migration rewrites it; a notice names both keys. CHANGELOG marks it breaking.
- [The migration writes an absolute, machine-specific path into `variants.yaml`] → only when old `.db` files exist, so the file is rewritten once; a committed `variants.yaml` shows the path in `git diff`, and the notice says why. A person who wants the new layout moves the files and deletes the key.
- [Old `.db` files next to an explicit `db.filename` are orphaned] → only the rename applies; CHANGELOG says to set `db.database` to the absolute `${slug}` form of the old directory.
- [The printed default is relative, so `config` does not show where one variant's file is] → `variant create` and `status` show the absolute file.
- [Implode removes the worktree and with it the SQLite file] → intended; `deprovision` removes the file first for the case that the worktree stays.
- [`SQLITE_DATABASE` in Mise now names the file of `main` and variants' sibling files, or the worktree-relative file] → documented in the Database page and the CHANGELOG; the `# from env` comment shows the source.
- [An absolute `db.database` makes state non-portable] → state files are local and uncommitted.
- [`database` as a new field on `VariantRecord` touches MCP, UI and extension fixtures] → test fixtures get the field; no behavior reads it except the CLI text.

## Migration Plan

No user action. A project with files in the former location gets `db.database` written once (decision 11); one without them starts on `.cache/variants/${slug}.sqlite`. A `variants.yaml` with `db.filename` is rewritten by the next `variant` command (tracked clean file) or after a `~` backup (untracked), as for other renames. Existing `state.yaml` of `main` heals on the next `provision`, `watch` or `create`. Rolling back leaves `database:` in a rewritten `variants.yaml`, which an earlier version reads as the PostgreSQL database name and ignores for SQLite.

## Open Questions

- Should `variant init` offer to pin `db.database` even for the default, so `variants.yaml` shows where files go? The spec says no for now (a minimal file); the Database page shows the default instead.
