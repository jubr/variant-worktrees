## Why

The `variant` CLI has ten subcommands (including `status` and `ui`), per-command flags (`--slug`/`-s`, `--detach`, `--stop`, `--force`, `--verbose`/`-v`), the global `--json` and `--yaml`, and short aliases. Users type them from memory or from `variant --help`. Shells cannot complete any of it, so every invocation costs a lookup, and a mistyped command only fails after the CLI starts.

## What Changes

- Add a `variant completions <shell>` command that prints a completion script for `zsh`, `bash`, or `fish` to stdout. The user sources it or saves it where the shell loads completions.
- The scripts complete the subcommands (with their descriptions where the shell supports them), the flags of each subcommand including aliases and CLI-only flags, the global `--help` and `--version`, and the `<shell>` argument of `completions` itself.
- The scripts also complete the value of `--slug`/`-s` and the positional slug of every subcommand that takes one, with the slugs of existing variants. The candidates come from `variant completions --list-slugs`, which prints one slug per line. In `zsh` and `bash` 4.1 or newer, the first completion on a `variant` command line gathers them in the background, so they are ready when the user reaches `-s`; they are kept in shell variables for 30 seconds, never in a file. `fish` and older `bash` gather on demand.
- The script content derives from the same command definitions that drive the CLI, so a new command or flag shows up in completions without a separate edit.
- `completions` appears in `variant --help`. It is a CLI-only command: it is not a lifecycle command, so it gets no MCP tool and no webview form, and it needs no configuration, database, or git repository.
- An unsupported or missing `<shell>` fails with a message that lists the supported shells and exits non-zero.
- Docs: install instructions for each shell in the README CLI section and the core guide; `CHANGELOG.md` records the addition.

## Capabilities

### New Capabilities

- `variant-cli/completions`: the `variant completions` command, the supported shells, what the generated scripts complete (subcommands, flags, slug values), the `--list-slugs` listing, and the failure behavior for an unsupported shell.

### Modified Capabilities

None.

## Impact

- `packages/variant-cli`: new `src/completions.ts` (script generators), `src/cli.ts` (register the command, extend the unknown-command check), tests under `test/`.
- `packages/variant-api`: new `src/list-slugs.ts`, exported as `listSlugs`, which reads local state files and worktree directories only.
- Docs: `README.md`, `docs/guide/core.md`, `CHANGELOG.md`.
- Specs: [specs/variant-cli/completions](../../specs/variant-cli/completions/spec.md).
- No new runtime dependency; the scripts are generated by plain string building, so the compiled single-file executable needs no extra files.

## Non-goals

- Completing slugs from the database. Candidates come from local variant state and worktree directories only, so completion never opens a database connection.
- Completing values other than slugs and shell names.
- Shells beyond `zsh`, `bash`, and `fish` (PowerShell, nushell, elvish).
- Installing the script for the user (no writes to rc files or completion directories).
- Completions for the MCP server or the VS Code extension.
