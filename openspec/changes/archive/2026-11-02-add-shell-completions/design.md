## Context

The CLI in `packages/variant-cli/src/cli.ts` builds its cleye subcommands from the shared `commands[]` list (`variant-api/commands`) plus the CLI-only `ui` command, and gives every lifecycle command the global `--json`/`--yaml` output flags. `commands[]` is also the source of MCP tools and webview forms, and its `name` is typed `keyof VariantClient`. Flags and aliases come from each command's `args` (`ArgDefinition.short` is the alias). `--help` and `--version` are cleye globals. The CLI also checks the first non-flag argument against `commands[]` to report unknown commands before cleye runs. See proposal.md for motivation.

The CLI ships three ways: from source, built `dist/`, and a `bun build --compile` single-file executable, so the feature cannot depend on files next to the binary.

## Goals / Non-Goals

**Goals:**

- Scripts for `zsh`, `bash`, `fish` that cannot drift from the real command and flag set.
- Zero work at load time: sourcing a script runs no `variant` process. At completion time, only a slug position runs `variant`, and it reads local files only: no database, no git, no writes.
- Works identically from source, `dist/`, and the compiled executable.

**Non-Goals:**

- Slugs known only to the database. See proposal non-goals.
- A generic completion framework or a new dependency.

## Decisions

**`completions` is a CLI-only command, outside `commands[]`.** `commands[]` entries are lifecycle operations typed against `VariantClient` and exposed over MCP and the webview. Completions are a shell integration with no meaning for either. It is registered next to the mapped commands in `cli.ts` as its own cleye command with a positional `<shell>`. The unknown-command check takes the union of `commands[]` names and `completions`. Alternative: add it to `commands[]` with a flag to hide it from MCP and webview; rejected because it would need a fake `VariantClient` method and filters in two other packages.

**Generate from a description model, not from cleye internals.** A small `describeCli()` in `completions.ts` returns `{ name, description, flags: [{ long, short?, description }] }[]` for every subcommand, built from `commands[]` (via `flagsFor`-equivalent logic: each `arg` becomes a flag with its `short`) plus the global output flags plus `ui` and `completions` themselves. Three string generators render this one model. The flag specs of a command, and the description and flags of `ui`, live in a small shared module (`cli-flags.ts`) so the CLI and the generator read the same objects; `--json`/`--yaml` come from `GLOBAL_FLAGS` in `output.ts`. Alternative: parse `variant --help` output at generation time; rejected as fragile and it would spawn work. Alternative: introspect cleye's command objects; rejected because cleye does not expose a stable public shape for that.

**Static tables, one dynamic callback for slugs.** Each script embeds the full command/flag tables, so completing a subcommand or flag costs only the shell's own work. The one exception is a slug position, where the script runs `variant completions --list-slugs 2>/dev/null` and offers its lines. The price of the static tables is that a user must regenerate the script after upgrading `variant`; the docs say so. Slugs are not embedded because variants are created and removed constantly; an embedded list would be stale within minutes. Alternatives: a hidden `variant __complete` entry point that answers every TAB (rejected: a process start per keypress for data that rarely changes, and a hidden command); a script regeneration hook after `create` and `implode` (rejected: writes into the user's shell setup).

**Prefetch into shell variables, stale-while-revalidate.** The list lives in variables of the running shell and nowhere else: no file, no marker, nothing outliving the session. Three variables per shell, namespaced `__variant_*`: the slugs, the directory (`$PWD`) they were gathered in, and the time they were gathered. Time comes from `$SECONDS` in bash (a builtin, no process), from `$EPOCHSECONDS` in zsh (builtin module `zsh/datetime`, no process; `$SECONDS` reads 0 inside completion functions, so it cannot be used), and from `date +%s` in fish. A completion request at any position compares the directory and age; at a slug position the remembered list is offered at once, fresh or stale. The window is fixed at 30 seconds: longer would miss newly created variants, shorter would start a process on most TAB bursts. An empty result is remembered too, so a non-project directory does not start a process on every keypress.

The earlier idea of a background process cannot set the parent shell's variables, so the result has to travel to the running shell some other way. What works without a file is a file descriptor opened on a process substitution in the current shell:

- *zsh.* `exec {fd}< <(variant completions --list-slugs 2>/dev/null)` followed by `zle -F $fd _variant_slugs_ready`. The handler runs inside the shell when the output is readable, reads it into the variables, unregisters the descriptor, and closes it. This is fully asynchronous: the list lands without any further keypress. A slug completion that finds the descriptor still open reads it directly (waits for the one gathering in flight) rather than starting another.
- *bash 4.1 or newer.* `exec {fd}< <(...)` stores the descriptor in a variable. At the next completion request the script checks `read -t 0 -u "$fd"`: when data (or end of file) is ready it reads the list with `mapfile -t -u "$fd"`, stores it, and closes the descriptor; when the process is still running it keeps offering the remembered list. With no remembered list at a slug position it blocks on `mapfile -u`, which waits for the gathering in flight. Process substitution adds no job to the table, so no job number prints. Bash has no event to push the result in, so it is picked up at the next completion request, not before; that is enough because the next slug TAB is a completion request.
- *fish and bash older than 4.1.* No prefetch. Fish cannot read a background result into a variable of the running shell: the options are a file or a universal variable, and a universal variable is persisted to disk and shared across all sessions, which is a cache by another name. Bash 3.2 (macOS `/bin/bash`) has neither `{fd}` allocation nor a fractional `read -t`. These shells gather synchronously at a slug position, remember the result in a global variable for 30 seconds per directory, and offer it. The only cost is that the first slug completion in a window waits for the listing (file reads only, no database or git). Alternative for fish: a universal variable written by `fish -c 'set -U ...' &`; rejected as above, and because slugs of one project would be offered to sessions in another.

All three keep `variant` from writing to the terminal by redirecting its stderr inside the substitution, and the smoke tests assert nothing is printed and no job remains. Sourcing the script still starts nothing; prefetching at shell start would add a process to every new terminal, including ones that never use `variant`, so the first TAB on `variant` is the signal that it is needed.

Alternatives: a long-lived background daemon per shell (rejected: lifecycle and cleanup for a few milliseconds of saving); a file cache under the user's cache directory (rejected by request, and it needs permission, atomic-write, and tamper handling that variables avoid); invalidating from `variant create` and `implode` (rejected: those run in other processes and cannot reach shell variables).

**Slug listing is a flag of `completions`, reading local files only.** The listing itself is `listSlugs` in `variant-api`, exported for the CLI, because the state rules it reads are internal to that package. `--list-slugs` is a boolean flag on the existing command, so there is no hidden subcommand and `<shell>` becomes optional only with it. It unions two sources: saved variant states (`stateSlugs` over the state directory) and directory names starting with `variant.prefix` below `variant.root` (prefix stripped), which also finds worktrees that were never provisioned. It does not call `createClient`, because that creates the state directory and a database adapter. The state directory path is computed by the same rule as `createClient` (`<configDir>/.cache/variants`), extracted into one helper both use so they cannot diverge. The database is skipped on purpose: `list` asks it, but completion must stay fast and work with the database down; a variant that exists only as a database schema with no state and no worktree is not offered. Directory names that are not valid slugs are skipped, so a stray `_v-foo bar` directory cannot put a word with a space on the command line. Any failure (no project, invalid config) is caught and yields empty output and exit code 0, so a TAB in an unrelated directory never prints an error into the prompt. `main` is not listed; it is derived from the primary checkout, not a variant that exists on disk. Alternative: reuse `list` and parse its JSON; rejected because it connects to the database.

**Shell specifics.**

Slug-taking subcommands are the ones whose definition has a `slug` argument; the model carries that as a per-subcommand `takesSlug` so the generators never hard-code the list.

- `zsh`: a `#compdef variant` function `_variant` using `_arguments` and `_describe` with descriptions; `--slug`/`-s` and the optional first positional use a `_variant_slugs` helper that fills candidates with `compadd` from the listing. The script ends with the usual dual-mode guard (`if [ "$funcstack[1]" = "_variant" ]; then _variant "$@"; else compdef _variant variant; fi`), so it works both as an autoloaded file in `$fpath` and under `eval "$(variant completions zsh)"` after `compinit`.
- `bash`: a plain function `_variant` using `COMPREPLY=($(compgen -W ...))` with a `case` on the subcommand, registered with `complete -F _variant variant`. No dependency on `bash-completion`. A slug is offered when the previous word is `--slug` or `-s`, or when the subcommand takes a slug and the current word does not start with `-`.
- `fish`: `complete -c variant` lines using `__fish_use_subcommand` / `__fish_seen_subcommand_from`, with `-d` descriptions, `-s`/`-l` for short and long flags, and `-f` to suppress file completion where only fixed values apply. Flags are scoped per subcommand. `--slug`/`-s` take the listing as their argument, and slug-taking subcommands offer it for the positional.

**Output and errors.** The script goes to stdout through the same path as other output, but unlike lifecycle commands it is printed raw (not JSON). Without `--list-slugs`, the shell argument is validated before anything else; a missing or unknown value throws the existing error style (`Unsupported shell: <x>. Supported shells: zsh, bash, fish.`), which the top-level handler prints to stderr with exit code 1. The command does not call `createClient`, which is what keeps it independent of the database and free of side effects; only `--list-slugs` loads the configuration, and it swallows load errors.

**Tests follow the TDD order.** High-level first: run the CLI entry (as `test/cli.test.ts` does) with `completions <shell>` and assert stdout, exit code, and error cases. Then coverage tests iterate `commands[]` and assert every name and flag appears per shell, plus a negative scenario (`--detach` and `--stop` only where they exist). Slug listing tests build a temporary project (state files, `_v-*` directories, a custom prefix) and assert the listing, the absence of side effects (no state directory created), output from the autodetected settings without a `variants.yaml`, and empty output for an invalid one. Slug completion tests check each script wires `--list-slugs` only into slug positions. A load smoke test runs each script through its real shell (`bash`, `zsh`, `fish`) when that shell is installed and is skipped otherwise, so CI on a machine without fish stays green while the check still runs where possible.

## Risks / Trade-offs

- [A slug TAB with nothing remembered waits for the listing] → Only the first slug completion in a directory (and, in fish and bash older than 4.1, the first in each 30 second window) pays it; the listing reads files only (no database, no git) and the compiled executable starts fast.
- [A variant created or removed within the last 30 seconds is not reflected on the next slug TAB in zsh and bash 4.1+] → The stale list is offered while gathering restarts, so the TAB after that is correct; the window is fixed and short. Fish and older bash gather on demand and are not affected.
- [Background output or job notices leak into the prompt] → Process substitution with stderr redirected inside it; no job is created. Smoke tests assert no output and no remaining job.
- [Shell variables collide with a user's own] → Everything is namespaced `__variant_*`.
- [A descriptor stays open if the user never completes again] → The gathering finishes on its own and the descriptor is closed with the shell; at most one is open at a time because a new gathering starts only when none is in flight.
- [A word with spaces or shell metacharacters ends up on the command line] → The listing only emits valid slugs, and the script quotes candidates when handing them to the shell.
- [Slugs that exist only as database schemas are not offered] → Accepted and documented; they have neither state nor worktree, so none of the slug-taking commands can resolve them to a worktree anyway.
- [Listing logic diverges from how `list` finds variants] → Both read the same state files and `<prefix>*` directories; a test asserts the listing equals the file-based slugs of `list` for a fixture project.
- [Script goes stale after an upgrade] → Documented: regenerate on upgrade; the `eval`/`source` forms regenerate on every shell start.
- [Quoting bugs for descriptions with `'`, `:`, or `$`] → Descriptions are escaped per shell in one helper each; a test feeds a description containing those characters through every generator.
- [Shell not installed in CI, so load tests skip] → The string-level coverage tests always run; the smoke tests run wherever the shell exists, including the contributor's machine.
- [Sharing the flag specs touches `cli.ts` behavior] → Pure move; the existing CLI tests cover the flags and stay green.

## Migration Plan

Additive. No migration, no config change. Rollback is removing the command; nothing persists on the user's machine unless they chose to save the script.
